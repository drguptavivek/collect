# MEDRES ODK Collect: RC4 Update - January 28, 2026

**GitHub Repository**: [drguptavivek/collect](https://github.com/drguptavivek/collect)  
**Release**: `v2025.3.3-MEDRES-RC4`

## Why This Update Mattered

RC4 was the release where MEDRES stopped treating all QR codes as equivalent. That was important because field medical research needs two distinct QR-driven workflows:

1. **Production onboarding**
   - Scan a MEDRES project QR
   - Stage project metadata
   - Login with credentials
   - Materialize the production ODK project

2. **Draft testing**
   - Scan a draft QR
   - Preserve the full draft URL
   - Enter **Draft Testing Mode**
   - Test a draft form without contaminating production onboarding

Without that split, test flows and production flows could bleed into each other.

## QR Type Detection

RC4 introduced explicit QR classification by URL shape:

| QR Type | URL Pattern | Behavior |
| :--- | :--- | :--- |
| MEDRES Project QR | `/v1/projects/<ID>` | Accepted, returns user to login |
| Draft QR | `/v1/test/<TOKEN>/projects/<ID>/forms/<FORM_ID>/draft` | Accepted, enters Draft Testing Mode |
| Standard ODK Managed QR | `/v1/key/<TOKEN>/projects/<ID>` | Rejected |

Two details matter:

- Classification is based on **URL shape**, not on server domain.
- In draft QRs, `project.name` is treated as **draft form display metadata**, not as the persistent production project name.

## What RC4 Changed

### 1. Draft testing became a separate path

Draft QRs no longer belong in the normal MEDRES login/tokenization flow. The intended behavior is:

- preserve the full draft URL
- avoid username/password login
- activate a dedicated draft-testing project context
- keep draft display metadata from overwriting production project identity

### 2. Project QR onboarding stayed explicit

MEDRES project QRs still require normal authentication. Their role is to stage:

- auth base URL
- Central project ID
- project name
- non-sensitive general settings
- admin settings

The actual ODK `server_url` is only materialized after successful login.

### 3. Standard ODK managed QRs were blocked

Standard ODK managed QRs already contain `/key/<TOKEN>/...` URLs. MEDRES rejects those because they bypass the MEDRES authentication model and can overwrite project configuration in unsafe ways.

## Security Notes

The QR pipeline now relies on structural validation rather than loose heuristics:

- compressed payload limit
- decompressed payload limit
- compression-ratio guard
- strict JSON parsing
- typed QR classification
- explicit rejection of malformed URLs
- staged writes only after successful parse/classification

This protects against oversized payloads, decompression abuse, malformed configuration, and accidental acceptance of incompatible ODK-managed QRs.

## Operational Outcome

For field teams, RC4 made the QR story much clearer:

- production project QR -> login -> production work
- draft QR -> Draft Testing Mode -> isolated testing
- managed ODK QR -> reject

That separation is what keeps draft experimentation from polluting real study configuration.
