## 1. Intelligent QR Code Type Detection - The Major Feature

**Problem**: Field medical research requires two distinct workflows:
1. **Production Data Collection**: Researchers scan Project QRs to collect real patient data
2. **Form Testing**: Research coordinators scan Draft QRs to test form updates before deployment

Standard ODK treats all QRs the same, creating confusion and potential data contamination (test data mixed with production data).

**Why This Matters**: In field medical research, form definitions change frequently as protocols are refined. Researchers need to test new form versions without disrupting ongoing data collection. The wrong QR scan could:
- Overwrite production server settings with test server URLs
- Mix test submissions with real patient data
- Break authentication by applying incompatible settings

**Solution**: The QR scanner now automatically detects QR type and applies appropriate behavior.

### QR Type Detection Matrix

| QR Type | URL Pattern | Scanner Behavior | Use Case |
|---------|-------------|------------------|----------|
| **MEDRES Project** | `/v1/projects/<ID>` (no `/key/`) | ✅ **Login Mode** | Production data collection |
| **Draft/Test** | `/draft` **AND** `/test/` | ✅ **Demo Mode** | Testing form updates |
| **Standard ODK** | `/key/<TOKEN>` | ❌ **Rejected** | Incompatible with MEDRES auth |
| **Legacy ODK** | Base64 encoded `/key/` | ❌ **Rejected** | Old ODK Central format |

### Workflow Examples

#### Scenario 1: Research Coordinator Testing New Form
1. Research coordinator generates Draft QR from ODK Central (form in draft state)
2. Scans QR on device
3. App enters **Demo Mode**: Shows "[Draft] Form Name" in project list
4. Coordinator tests form, submits test data
5. Test submissions go to draft endpoint, isolated from production data

#### Scenario 2: Field Researcher Collecting Data
1. Field researcher scans Project QR (generated for their study site)
2. App prompts for login credentials
3. After PIN setup, app enters **Production Mode**
4. Researcher collects real patient data
5. Submissions go to production project endpoint

#### Scenario 3: Accidental Standard ODK QR Scan
1. Researcher accidentally scans standard ODK Central QR (from different project)
2. App detects `/key/` token in URL
3. **Rejects QR** with error: *"This QR code is for standard ODK Central and cannot be used with MEDRES. Please scan a MEDRES project QR code."*
4. No settings changed, authentication remains intact

## 2. Automatic Project Name Updates

**Problem**: After successful login, the app displayed "MEDRES Project #12" instead of the actual project name (e.g., "Diabetic Retinopathy Screening - Tamil Nadu"). This persisted until the user manually refreshed project details.

**Why This Matters**: In multi-site field research, data collectors need immediate visual confirmation they're working in the correct study project. The generic label created confusion and potential data entry errors.

**Solution**: The app now automatically fetches and updates project details from the server immediately after PIN setup or PIN entry.

**Implementation**:
- Added `fetchAndUpdateProjectDetails()` to `MedresAuthManager`
- Integrated with `SetupPinActivity` (first-time setup) and `PinEntryActivity` (returning users)
- Background update for returning users, immediate UI refresh for new setups

**Result**: Dashboard shows correct project name within 1-2 seconds of authentication.

## 3. QR Code Security Hardening

**Problem**: QR codes are untrusted input. Malicious or malformed QR codes could:
- Crash the app (decompression bombs: 4KB → gigabytes)
- Inject invalid settings keys
- Override sensitive authentication parameters
- Cause Out-of-Memory errors

**Why This Matters**: In a hospital environment, QR codes might be shared via email, printed posters, or third-party tools. We cannot assume all QRs are generated by trusted sources.

**Solution**: Implemented five layers of validation before applying any QR settings.

### Security Layers

#### Layer 1: Size Limits
- Compressed payload: Max 4KB
- Decompressed payload: Max 16KB  
- Compression ratio: Max 4:1

**Prevents**: Decompression bomb attacks (tiny QR expands to crash app)

#### Layer 2: Key Validation
- General settings: Validated against `ProjectKeys` (ODK's official setting keys)
- Admin settings: Validated against `ProtectedProjectKeys`
- Invalid keys: Logged and skipped

**Prevents**: Injection of arbitrary preference keys

#### Layer 3: Type Safety
- Boolean values: Must be `true`/`false`
- String values: Must be valid strings
- Integer values: Must be valid integers
- Admin settings: Must be boolean only

**Prevents**: Type confusion attacks

#### Layer 4: Sensitive Key Protection
These keys are **blocked** from QR override:
- `server_url` (handled by login flow)
- `username` (handled by login flow)
- `password` (never in QR)
- `protocol` (enforced by app)

**Prevents**: Credential theft via malicious QR

#### Layer 5: Demo Mode Validation
Draft QRs must contain:
- `/draft` in URL
- `/test/` in URL
- Both conditions required

**Prevents**: Accidental production data in test mode

## Technical Context: MEDRES Architecture

MEDRES implements four major modifications to standard ODK Collect:

### 1. Custom Authentication
- **Standard ODK**: Basic Auth (username/password in every request)
- **MEDRES**: Bearer Token (short-lived JWT, 3-day validity)
- **Why**: Server-side revocation, offline grace period (6 hours), better security

### 2. Local Networking (Debug Only)
- **Feature**: Android Emulator resolves `central.local` to `10.0.2.2`
- **Why**: Enables local development without modifying `/etc/hosts` on emulator
- **Security**: SSL bypass only in debug builds

### 3. PIN Security
- **Feature**: Mandatory 4-digit PIN after login
- **Why**: Protects against unauthorized device access in shared-device environments
- **Security**: 3 failed attempts = immediate wipe, PBKDF2 hashing

### 4. Project Persistence
- **Feature**: Manual project configuration persists correctly
- **Why**: Standard ODK had bugs with manual server entry
- **Implementation**: Uses ODK's internal preference schemas (`general_prefs`)

---

## Security Design Decisions

### Bearer Token vs Basic Auth
**Decision**: Replace Basic Auth with Bearer Token  
**Rationale**: Short-lived tokens (3 days) improve security, enable server-side revocation, support offline grace period  
**Implementation**: OkHttp interceptor injects token into all OpenRosa requests

### PIN Security on Top of Auth
**Decision**: Mandatory local PIN in addition to server credentials  
**Rationale**: Protects against unauthorized device access, 3-attempt wipe prevents brute force, works offline  
**Implementation**: PBKDF2 hashing stored in `medres_auth_secure` (hardware-backed encryption)

### Forms Wiped, Instances Preserved
**Decision**: Delete blank forms on logout, keep filled instances  
**Rationale**: Prevents new users from seeing old project forms, allows shared device workflows (User A fills, User B uploads)  
**Implementation**: `ProjectResetter` with `RESET_FORMS` only

### Grace Period for Offline Work
**Decision**: 6-hour grace after token expiry  
**Rationale**: Field workers may have spotty connectivity, hard expiry would strand users offline  
**Implementation**: `GRACE_PERIOD_MS = 6 * 60 * 60 * 1000`, server reachability check prevents unnecessary lockouts
